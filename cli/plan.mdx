---
title: "stb plan"
description: "Preview direct rebuilds or virtual-environment deployments without mutating ClickHouse."
---

Compare the compiled project with ClickHouse and print a read-only warehouse plan. A successful
command assembles the complete workflow that a build would execute against the same observed state,
then atomically publishes its JSON and exact SQL without mutating ClickHouse.

```bash
stb plan
stb plan --select orders
stb plan --select pipeline:order_events --json
stb plan --deployment-id 20260701T120000Z_release202607
stb plan --verbose
stb plan -v
```

The effective project mode chooses the planner:

- **Direct mode:** plan the requested destructive rebuild. No selector means every model; selectors
  include downstream closure. Matching objects are not pruned.
- **Virtual environments:** plan changed deployment objects, replay roots, and policies against
  published and staged state.

Use `--deployment-id` in virtual-environment mode to inspect exact deployment-specific physical
names. Its timestamp prefix also fixes the deployment creation timestamp, so unchanged warehouse
state and the same explicit identity produce deterministic workflow bytes. If omitted, `plan`
generates a disposable preview identity.

## Selection

Repeat `--select` to union bare model names and `pipeline:<name>` selectors:

```bash
stb plan --select orders --select region_lookup
```

Graph `+` syntax, tags, paths, globs, and exclusions are not supported by `plan`.

## Replay controls

```bash
stb plan --select orders --full-refresh
stb plan --select orders --start-time 2026-07-01T00:00:00Z
```

Both require `--select` and are mutually exclusive.

`--full-refresh` applies only to virtual environments. `--start-time` applies to both modes. In
direct mode it shows the effective start time in plan text and the nullable top-level `start_time`
field in plan JSON, and the exact workflow SQL includes every lower frontier used for preflight,
coverage capture, and replay. Direct replay inputs must already exist and expose timestamp or
landed-at lineage through the selected closure.

## Common options

Connecting commands accept `--host`, `--port`, `--username`, `--password`, `--database`,
`--target`, `--vars`, and `--project-dir`. `--json` emits structured output and `--verbose` (`-v`)
includes full schema diffs.

## Exact workflow artifacts

After read-only connected inspection, StreamBuild atomically replaces the complete directory:

```text
target/run/plan/
├── plan.json
├── workflow.sql
└── steps/
    ├── 0001_<step-id>.sql
    └── ...
```

The bytes printed by `stb plan --json` are exactly the bytes stored in `plan.json`; text mode writes
the same JSON through the same serializer. Each numbered file is byte-identical to its workflow
statement, and `workflow.sql` is those statements joined in order.

Plan and build use the same connected preparation, workflow assemblers, ordering validation, and
artifact serializer. They remain independent invocations: `stb build` inspects current warehouse
state again and never reads, compares, promotes, or executes `target/run/plan/`. Warehouse changes
between commands can therefore produce a different build workflow; build preflight assertions
protect the state observed during its own preparation.

All `target/run/` files are disposable visibility output, not local state. Failed compilation,
connected inspection, workflow assembly, or publication leaves any previous complete plan artifact
unchanged.
